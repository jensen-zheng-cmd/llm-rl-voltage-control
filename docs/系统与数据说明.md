## 3. 一天有多少点

当前源文件时间间隔为3分钟，因此：

\[
24\times60/3=480\quad\text{个功率区间/完整24小时}.
\]

目标论文日内控制间隔为15分钟，因此：

\[
24\times60/15=96\quad\text{步/日}.
\]

所以源文件的点确实更密，是目标控制间隔的5倍；后续按5点聚合到15分钟。若原值代表各3分钟区间的平均功率，15分钟平均功率取5个值的算术平均；只有计算能量时才乘时间间隔，不能把5个功率值直接相加当作新的功率。

“文件每3分钟一条”不等于原始仪表原生每3分钟采样，发布数据可能已经过插值等处理。v1按区间右端点解释并以5点平均聚合，这是明确记录的工程约定；实现与结果见 [环境验收说明](环境验收说明.md)。

完整文件的首尾时间、行数、各自然日记录数、时间间隔及空值标记扫描，均保存在[时间轴核验](../support/evidence/case33_download_manifest.json)。这些来源检查不等同于全部物理数值与潮流场景审计；后续进度统一见TASKS。

## 4. 后续如何训练和验证

- 历史P/Q负荷与PV有功是外生输入，PPO在潮流环境中生成自己的动作和奖励，无需专家动作标签。
- 按完整日或连续时间块划分train/validation/test，不随机打散相邻采样点；具体日期清单留待数据预处理阶段冻结。
- LLM经验库、Reflexion、PPO预训练和微调使用训练日；验证日用于选参数/checkpoint；最终测试日评估冻结策略。
- 日前只给区域小时预测，真实未来数据留在环境中；日内按时刻提供当前量测。
- 归一化、容量估计和缩放仅使用训练部分确定。PV无功上限随当前有功变化，但额定容量在训练和测试之间保持固定。

机器可读配置见[system_selection.json](../configs/system_selection.json)。
